# OAuth receipts: isolated single-device candidate
Reuse the existing dedicated-device pattern from TaxiRefundBridge, never its refund credential. No client secret or SumUp token on Android. Configure fresh separate high-entropy TAXI_RECEIPT_DEVICE_TOKEN and 32 random bytes in hex TAXI_RECEIPT_ENCRYPTION_KEY in Supabase, not in source, logs or chat. Merchant is fixed by dedicated TAXI_RECEIPT_MERCHANT or the existing server-only TAXI_REFUND_MERCHANT (read-only use). Existing OAuth client secrets remain as configured. No static SumUp API key needed.

Deployment gate: apply reviewed storage.sql as a new isolated migration; verify RLS and privileges, confirm merchant response schema, run integration tests, then deploy only the new taxi-sumup-oauth function with verify_jwt=false (external browser callback authenticates using atomically consumed expiring state; every POST has a separate device credential). Never disable JWT verification globally. No existing function, payment, refund or ledger modification. User must configure the dedicated device token in the Android keystore and consent via SumUp in their browser. Verify negative unauthenticated calls and real receipt before releasing signed APK. No actual deployment is claimed.

The transaction GET is explicitly documented with transactions.history. The receipt-details documentation has conflicting cached/current scope descriptions; retain the known single-transaction route until live access is verified. No extra scopes.
